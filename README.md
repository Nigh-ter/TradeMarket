# TradeMarket

**A complete player-driven economy for Minecraft Paper servers** — global market, timed auctions, escrowed buy orders and an offline mailbox, built on a single-threaded transaction model that makes item/money duplication structurally impossible.

## Why this plugin exists

> **Disclaimer:** I am not a professional programmer. This plugin was built, reviewed and iterated with AI coding tools and large language models — I provide the requirements, do the acceptance testing and handle maintenance, while the actual implementation is AI-driven. It has been tested and works on a local Paper 1.21 server, but I cannot guarantee it covers every edge case

The first version of this plugin was generated by an AI coding tool. The feature list looked complete — market, auctions, mailbox, admin compensation, hooks into other plugins — but almost nothing actually finished: players paid and received no item, auction countdowns drifted, mail was stuck in "processing" forever, and language keys rendered as raw `<gui.button.xxx>` on screen. It compiled, it started, the GUIs opened, and **not one end-to-end flow worked**.

Patching that foundation was pointless: the problem was not a line of code but the architecture. This version is a rewrite that fixes the rules first — *main-thread serialisation, two-phase commit, everything delivered through the mailbox* — and only then adds features. One feature fewer is better than one more button that looks fine and eats money.

### What was actually wrong with 1.x

The 1.x lineage of this plugin had a fatal design flaw: it released database work onto async threads and then touched the Bukkit API from there. In practice that meant purchases that took the player's money and never delivered the item, with no error shown to anyone, plus a cascade of leaked locks that eventually froze the server's economy.

This version is a ground-up rewrite built around one rule:

> **Every business state change happens on the main thread, serially. No business locks exist, because nothing runs concurrently.**

The database is still synchronous (SQLite in WAL mode, sub-millisecond local writes); what changed is that ordering is now guaranteed instead of hoped for.

| 1.x problem | How it is solved here |
|---|---|
| Lock released on a DB thread → exception, money taken, no delivery, lock leak | All business mutations run serially on the main thread |
| Vault called inside a DB transaction, rollback does not roll back money | **Two-phase commit**: guarded write first (conditional `UPDATE ... WHERE status='ACTIVE'`), then money, then delivery — any failure rolls the whole thing back |
| Items delivered straight to the inventory and lost when it was full | **Everything is delivered through the mailbox**; a full inventory only delays collection, it never destroys items |
| Systematically misaligned language keys (`<gui.button.xxx>` on screen) | Language keys are self-checked against the code at startup; missing keys are reported one by one |
| Half-finished features (buy orders, search, reward centre) | Only complete loops ship: market, auction, mailbox, buy orders, plus admin tooling |

## Features

### Market
- GUI browser with category tabs (all / weapons / tools / armour / blocks / food / misc)
- Price-range filtering and name sorting
- Shulker-box preview: right-click a shulker listing to see its contents without opening it
- Vanilla-translatable item names — Chinese clients see 橡木原木, renamed items keep their custom name
- Configurable sale tax, listing fee, listing cap, expiry and a material blacklist
- Anti-typo confirmation when a price deviates from the recent average by more than a configurable factor

### Selling and buy orders
- `/tk sell <price> [amount]` lists the held item; the price is **per unit**, the whole stack is sold as one lot
- `/tk order <price> [amount]` posts a buy order with the full amount escrowed up front
- Buy orders are not fulfilled instantly: a seller delivers the goods into escrow, the buyer inspects the offer in the mailbox and accepts or declines it
- Offers time out automatically (configurable) and escrowed goods return to the seller; cancelling an offer early costs a fee

### Auctions
- Bid escrow: the moment you bid, the money leaves your balance; outbid bidders are refunded immediately
- Buyout price acts as a hard ceiling — a bid at or above it wins instantly
- Anti-snipe: a bid in the last N seconds extends the auction
- Countdown broadcasts with a clickable `[Open auction]` button, win broadcasts, and full bid history per auction

### Mailbox
- Item, money and command mail; command mail runs as console with `%player%` substituted, so any plugin with a "give" command can be plugged in
- Works for offline players; unclaimed mail is never purged, claimed mail is cleaned up after N days
- Player-to-player sending (`/tk send`) with an optional fee and a confirmation GUI; tab-completion lists online players, offline recipients require the full name
- Unclaimed-mail notification on join, plus a second reminder for old unclaimed mail

### Administration
- `mail` / `mailonline` / `mailall` all open a confirmation GUI showing exactly what will be delivered before anything is sent
- `mailundo` to revoke a batch, `refund` for emergency top-ups, `redeliver` to re-deliver stuck items, `stats` for live counters
- Every transaction is written to a `tm_txlog` ledger, which is the source of truth for manual recovery

### Server integration
- **Vault** economy required; **LuckPerms** optional for per-group limits (e.g. `vip` may hold more buy orders)
- Custom-item awareness: ItemsAdder, Oraxen, MMOItems and MythicMobs items are tagged with their provider on the way in, and buy orders match on that tag
- Per-world restrictions: disable trading in named worlds, or allow only specific subcommands there
- Full `zh_CN` / `en_US` language files, switchable at runtime with `/tk reload`

## Installation

1. **Requirements:** Paper 1.21.x (built against 1.21.11), Java 21, and **Vault + any Vault economy plugin** (EssentialsX, CMI, …).
2. Drop `TradeMarket-1.0.0.jar` into `plugins/` and start the server.
3. On first start the plugin creates `plugins/TradeMarket/` with `config.yml`, `lang/zh_CN.yml` and `lang/en_US.yml`, and creates its SQLite database at `plugins/TradeMarket/market.db`.

> **Upgrading from 1.x:** an old configuration is backed up wholesale to `plugins/TradeMarket/backup-v1-<timestamp>/` and regenerated. 1.x test data is intentionally **not** migrated — the database is a fresh `market.db`.

The plugin **starts up and reports missing language keys** instead of silently rendering raw keys. If a language file is missing entirely it is recreated; edits to existing files are never overwritten.

| `/tk auction` / `/tk ah` | Open auctions | `trademarket.auction` |

| `/tk help` | Help (admins also see the admin section) | `trademarket.use` |
| `/tk reload` | Reload config and language files | `trademarket.admin` |
| `/tk admin help` | Admin command overview | `trademarket.admin` |
| `/tk admin mail <player> <item\|money\|command> [...]` | Mail a single player | `trademarket.admin` |
| `/tk admin mailonline <item\|money\|command> [...]` | Mail every online player | `trademarket.admin` |
| `/tk admin mailall <item\|money\|command> [...]` | Mail **every** player, including offline ones | `trademarket.admin` |
| `/tk admin mailundo` | Revoke a mail batch | `trademarket.admin` |
| `/tk admin refund <player> <amount>` | Emergency balance top-up | `trademarket.admin` |
| `/tk admin redeliver <auction\|listing> <id>` | Re-deliver a stuck item (the id is printed to console) | `trademarket.admin` |

All three mail commands open a confirmation GUI before sending. Money arguments accept `k` / `w` / `m` suffixes (`1k` = 1000, `1w` = 10000, `2m` = 2000000) and the configured currency symbol.

## Configuration

`plugins/TradeMarket/config.yml` is fully commented. Highlights:

- **Economy** — currency symbol, sound effects
- **Market** — min/max price, listing fee, tax, listing cap per player, expiry days, price-confirmation multiplier, material blacklist
- **Auction** — start-price bounds, minimum increment, default/max duration, tax, anti-snipe window and extension, countdown broadcast seconds
- **Buy orders** — broadcast toggle, per-player cap (with LuckPerms group overrides), max amount, tax, offer timeout, early-cancel fee
- **World limits** — globally disabled worlds plus an optional per-world subcommand allow-list
- **Data hygiene** — ledger retention, terminal-record retention, average-price window
- **Mailbox** — join notification, claimed-mail purge, old-mail reminder, player-to-player fee

Values are reloaded with `/tk reload`; nothing needs a restart except changes that touch the database schema.

## Architecture

For maintainers, in one screen:

- **Threading model.** Every business operation (list / buy / bid / settle / collect) runs serially on the main thread. The in-memory maps are authoritative state; SQLite (WAL, `synchronous=NORMAL`) is written synchronously, which costs sub-millisecond locally and buys total ordering.
- **Two-phase commit** for market purchases, auction settlements and mail collection:
  1. *Guarded write*: `UPDATE ... SET status='SOLD' WHERE id=? AND status='ACTIVE'` — only continue when exactly one row changed, so double-clicks and crashes cannot settle twice.
  2. *Money in → money out → deliver*; any failure reverts the status and refunds in full.
  3. Successful mailbox delivery is the point of no return; a catastrophic failure after it is recovered from the `tm_txlog` ledger via `/tk admin redeliver`.
- **Auction escrow.** Bids debit immediately; the previous top bidder is refunded immediately. A failed database write reverts both memory and money. Cancellation is only possible while there are no bids.
- **Item serialisation.** Bukkit `BukkitObjectOutputStream` + Base64 into a text column, preserving NBT. A row that fails to deserialise yields `null`, is marked `BROKEN` and skipped — one corrupt row never breaks a GUI.
- **Startup self-check.** Missing language keys are reported line by line; corrupt item rows are quarantined.
- **Zero bundled dependencies.** The jar ships no shaded libraries — the SQLite driver, Adventure and Vault are provided by the server at runtime.

## Building from source

No Gradle, no Maven, no network required — a single `javac` call via `build.cmd`:

```bat
build.cmd
```

Output: `dist/TradeMarket-1.0.0.jar`.

Compile-time references live in `libs/` (Paper API 1.21.11, Vault, Adventure, LuckPerms). They are **compile-only** and are deliberately excluded from this repository — drop the matching jars into `libs/` before building:

- `paper-api-1.21.11-R0.1-SNAPSHOT.jar` (PaperMC repository)
- `Vault.jar` (VaultAPI)
- Adventure API + text serialisers (Maven Central, or take them from the Paper API's transitive set)
- `LuckPerms-Bukkit-5.5.53.jar` (optional, for the group-limit hook)
- `guava`, `snakeyaml`, `sqlite-jdbc` (transitive compile references)

Offline self-checks live in `tools/` (`SelfCheck.java`, `EdgeCheck.java`) and cover language-key alignment, money parsing and the SQLite DDL.

## Known limitations

- SQLite single-file storage: **no cross-server sharing**. Multi-server networks need a different backend.
- Vault has no transactions, so the balance change and the database write cannot be made atomic. A hard kill of the server process leaves a tiny inconsistency window; `tm_txlog` is the arbiter and `redeliver` / `refund` are the repair tools.
- Custom items from plugins other than ItemsAdder / Oraxen / MMOItems / MythicMobs are not explicitly identified — vanilla NBT serialisation usually carries them, but this is not guaranteed.
- Not Folia-compatible (`folia-supported: false`).
